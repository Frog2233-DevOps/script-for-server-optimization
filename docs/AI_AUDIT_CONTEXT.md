## 1. Что это и какова история аудитов

Скрипт первичной настройки (bootstrap/hardening) Ubuntu-сервера 24.04/26.04,
~750 строк bash. История:

| Версия | Что произошло |
|---|---|
| v1.0.x | Генерация нейросетью по мотивам Habr/Telegraph/Linux-Optimizer |
| v1.1.0 | **Первый независимый аудит** (вторая модель, роль Senior DevOps/Security, чек-лист 12 блоков, балльная система, обязательная самопроверка). Критических дефектов не найдено; архитектура усилена: транзакционный откат SSH (`SSH_TXN`+`trap`), идемпотентный `write_file`, валидация аргументов до первого изменения системы |
| v1.2.0 | **Второй независимый аудит** той же методикой. Вердикт: 8.8/10 «требует доработки», 0 критических. 8 предупреждений исправлены |

Результаты обоих аудитов и описание методики — в git-истории и docs/DOCUMENTATION.md.

## 2. Осознанные решения — НЕ считать багами

Ниже решения, которые выглядят подозрительно, но являются продуманным дизайном.
Если ты считаешь, что какое-то из них всё же ошибочно — аргументируй отдельно,
ссылаясь на конкретную строку.

1. **sudo NOPASSWD:ALL** — осознанный компромисс: у созданного пользователя нет
   пароля по дизайну, значит парольный sudo невозможен. Компрометация ключа = root.
   Отмечено в комментарии в коде и в DOCUMENTATION.md §4.
2. **Переходные порты SSH остаются открытыми** — намеренно: закрытие до ручной
   проверки нового входа = риск локаута. Скрипт напоминает закрыть их в финале
   (`ufw delete allow <старый>/tcp`).
3. **ufw не включился → только warning** — в контейнерах/LXC без netfilter
   это ожидаемо; падение скрипта тут не помогло бы.
4. **kernel.panic=10** — автоперезагрузка после паники; на железе без kdump
   возможен boot loop. Известно, задокументировано (W10). Альтернатива (kdump)
   выходит за scope bootstrap-скрипта.
5. **Docker из репозитория Ubuntu (docker.io), а не официального repo.docker.com** —
   сознательный выбор: никаких сторонних GPG-ключей и репозиториев, security-
   обновления через unattended-upgrades.
6. **`--force` обходит все проверки версии ОС** — флаг называется именно так
   и документирован в usage; его назначение — ручной override.
7. **swap-файл, а не раздел** — стандарт для VPS; атомарное создание через
   временный файл + rename.
8. **AllowTcpForwarding local** — не `no`, а локальный форвардинг: типичная
   потребность (туннели к БД и т.п.) при закрытом GatewayPorts.
9. **Нет отключения IPv6** — не требуется целевым сценарием; default deny UFW
   покрывает обе стеки (IPV6=yes в ufw по умолчанию).
10. **Нет AIDE/auditd/rkhunter** — выходит за scope «первая настройка для
    личного/небольшого VPS»; скрипт позиционируется честно.

## 3. Что уже проверено дважды (не трать на это шаги)

- `bash -n` — синтаксис чист;
- парсер аргументов: `--help` → 0, неизвестный флаг → 2 + usage на stderr;
- транзакция SSH: все пути выхода между `SSH_TXN=1` и `SSH_TXN=0` идут через
  `on_exit` → `rollback_ssh` (проверено ревью, все ветки die/restart/Ctrl+C);
- идемпотентность: write_file (cmp), ufw_allow (status check), merge ключей
  (awk-дедуп), grep-before-append (fstab, .bashrc, sudoers), замена 127.0.1.1;
- права на критичные файлы: authorized_keys 600/владелец, sudoers 0440,
  bootstrap.log 0600, WORKDIR/swap umask 077;
- конфликты значений sshd: префикс `00-` drop-in + проверка `N_ALLOW==1`
  перекрывают 50-cloud-init.conf и чужие drop-in'ы.

## 4. Методика, которой придерживались предыдущие аудиты

Рекомендуемая и для тебя. Роль: пессимистичный Senior DevOps/Linux Security
Engineer. 12 блоков по 0–10 баллов:

1. Безопасность · 2. Идемпотентность · 3. Обработка ошибок ·
4. Совместимость · 5. Права/root · 6. Сеть и доступность ·
7. Логирование · 8. Обновления · 9. Ресурсы · 10. Атомарность/откат ·
11. Читаемость · 12. Edge cases.

Итог = среднее; категории: ≥9.0 production ready, 7.0–8.9 требует доработки,
4.0–6.9 небезопасен, <4 опасен.

**Обязательные правила честности:**
- каждая претензия — с цитатой точной строки скрипта;
- неуверенность помечай «требует проверки на целевой системе», а не выдавай
  за факт (статически недоказуемо: поведение KillMode ssh.service при
  socket-активации 24.04, версионные особенности ufw);
- перед финалом — самопроверка: прошёл ли ты все строки, нет ли галлюцинаций,
  не пропустил ли очевидное (взгляд злоумышленника + взгляд админа в 3 часа ночи).

## 5. Известные остаточные риски (проверяй, закрыты ли они, а не «найди заново»)

| ID | Риск | Статус |
|---|---|---|
| R-wrong-key | Валидный по форме, но чужой ключ → локаут. Скрипт физически не может проверить приватную пару. Митигация: отпечатки в лог + предупреждение про rescue-консоль. Roadmap: двухфазный режим --stage-keys/--finalize | открыт, митигирован |
| R-nopasswd | NOPASSWD sudo: ключ = root | осознанно (см. §2.1) |
| R-panic | kernel.panic=10 без kdump → boot loop на железе | открыт, задокументирован |
| R-docker-ufw | Docker пробивает UFW для -p портов (свойство Docker) | предупреждение в выводе |
| R-github | --github доверяет аккаунту GitHub | предупреждение в выводе, сверка отпечатков обязательна |

## 6. Как сообщать о находках

Открывай issue или PR с форматом:

```
[BLOCK N] краткое описание
Строка: <цитата>
Риск: <что произойдёт, сценарий>
Серьёзность: critical / warning / nit
Предлагаемый фикс: <код/подход>
Проверено ли на живой системе: да/нет
```

Находки без цитаты строки и без сценария воспроизведения будут закрываться
как «не подтверждено» — правило введено после опыта первого аудита.
